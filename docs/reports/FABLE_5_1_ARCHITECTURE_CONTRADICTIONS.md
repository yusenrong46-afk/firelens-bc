# FireLens architecture: documentation vs. code vs. runtime

Date: 2026-09-03. Starting commit `b24a73bb` (also the production build).

Method: the code path and the running product were mapped first (PASS A), and
only then were `README.md`, `docs/ARCHITECTURE_V1_6.md`, the ADRs, the Product
Constitution and the same-day stabilization notes read (PASS B). Each row
compares a documented claim with what the source and the running application
actually do. Verdicts: **Agree**, **Partial**, **Disagree**.

## Summary

The documents describe an intended architecture — one typed parse, one
immutable plan, one result set — that the code approximates but does not
implement. The gap is not in the safety invariants (failure ≠ zero, no
personalized decisions, no fabricated official records all hold at runtime) but
in *understanding*: many overlapping phrase grammars decide location, clause
shape and record reference, and the "sole authority" plan is downstream of all
of them. Presentation and deployment claims (visible proof, on-demand map,
static asset directory) are the furthest from runtime reality.
